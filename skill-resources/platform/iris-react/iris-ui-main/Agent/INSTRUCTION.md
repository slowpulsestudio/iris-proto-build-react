# Figma Implementation Agent

## Mission

1. Implement Angular components for all Figma pages marked "Ready for dev" (✅) that are not yet in the codebase
2. Revisit already-implemented components and update them if the Figma design has changed
3. Push each change directly to `main`

## Conventions

### Paths (relative to repository root)

| Path                              | Purpose                                                    |
| --------------------------------- | ---------------------------------------------------------- |
| `Agent/figma.config.json`         | Figma file URL                                             |
| `Agent/component-hints/<slug>.md` | Per-component functional requirements                      |
| `Components/src/lib/<slug>/`      | Angular component files                                    |
| `Components/src/public-api.ts`    | Barrel exports                                             |
| `Components/src/styles/`          | Token & typography SCSS — **read before writing any SCSS** |
| `Storybook/<slug>/`               | Storybook stories and MDX docs                             |

### Naming

| Source          | Result                     |
| --------------- | -------------------------- |
| Figma page      | `Component / Button Group` |
| Slug            | `button-group`             |
| PascalCase      | `ButtonGroup`              |
| Component class | `IrisButtonGroupComponent` |
| Selector        | `iris-button-group`        |
| File prefix     | `button-group`             |

Slug derivation: take the part after `Component / `, lowercase, replace spaces with hyphens.

### Variable and identifier names

Never use abbreviated names for **variables, class names, interface names, type aliases, or private fields**. Use full, descriptive names at all times — in component classes, templates, specs, and stories.

**Forbidden:** `el`, `btn`, `evt`, `cfg`, `idx`, `len`, `val`, `dst`, `ref`, `fn`, `cb`, `ctx`, `msg`, `num`, `str`, `arr`, `obj`, `tmp`, `ret`, `err`, `res`, `req`, `dist`, `rect`, `raw`, `prev`, `curr`, `next` (when used as a generic alias rather than a clear domain term).

**Examples:**

- `el` → `buttonElement`, `linkElement`, `inputElement` (name after what it holds)
- `btn` → `nativeButton`, `switchButton`
- `rect` → `boundingRect`
- `raw` → `rawValue`
- `dist` → `distanceToLow`, `distanceToHigh`
- `next` (as a generic temp var) → `nextValue`, `nextState`
- Private fields: `_el` → `_elementRef`

**This rule does NOT apply to string literal values.** Abbreviations in string literals are allowed when they come from Figma design specs or design tokens (e.g. `'sm'`, `'md'`, `'lg'`, `'xs'` as size values; CSS custom property names like `--shadow-sm`). These are part of the design system contract and must not be changed.

## Step 1 — Read the Token System

Read **all** token files inside `Components/src/styles/`:

- `_tokens.scss` — imports all token packages and defines base CSS reset + global typography (`html`, `body`)
- `styles.css` — font barrel; consumers add this to their `angular.json`

All tokens are generated by the `Tokens` package (`Tokens/scripts/generate-tokens.mjs`) from JSON sources in `Tokens/src/` and imported by `_tokens.scss` via:

- `@oneidentity/iris-ui-tokens/dist/tokens.primitives` — raw colour palette (`--oi-color-<hue>-<shade>`), font families, font sizes, font weights, line heights, motion durations
- `@oneidentity/iris-ui-tokens/dist/tokens.typography` — theme-invariant typography aliases (`--oi-text-heading-*`, `--oi-text-body-s-*`, `--oi-text-caption-*`, `--oi-text-code-*`), generated from `Tokens/src/Typography.tokens.json`; emitted once at `:root`
- `@oneidentity/iris-ui-tokens/dist/tokens.light` / `tokens.dark` / `tokens.hc-light` / `tokens.hc-dark` — semantic tokens: `--oi-border-radius-*`, `--oi-spacing-*`, `--oi-background-color-*`, `--oi-button-*`, `--oi-content-color-*`, `--oi-border-color-*`, `--oi-motion-*`, etc.
- `@oneidentity/iris-ui-tokens/dist/tokens.custom` — generated from `Tokens/src/Custom.tokens.json`; contains per-theme shadows (`--shadow-sm`, `--shadow-base`, `--shadow-lg`, `--oi-shadow-low`) and focus ring (`--oi-focus-ring`)

You must use the actual CSS custom property names defined there in all generated SCSS.
Hard coded values are only allowed if no token is available for the value.

## Step 3 — Discover Ready-for-Dev Components

Use the Figma REST API to list all pages. The `FIGMA_PAT` environment variable contains
the personal access token for authentication.

```bash
# Fetch file structure (pages are in document.children)
curl -sS -H "X-Figma-Token: $FIGMA_PAT" \
  "https://api.figma.com/v1/files/<FILE_KEY>?depth=1" | jq '.document.children[] | {id, name}'
```

Filter the returned list to pages whose name matches the pattern `✅ Component / <Name>`
(i.e. starts with a ✅ emoji followed by `Component / `). The ✅ prefix marks the page as
ready for dev. Strip the `✅ ` prefix before deriving the slug.

For each matching page, fetch its full node tree to find the component/frame structure:

```bash
# Fetch a specific page's full node tree
curl -sS -H "X-Figma-Token: $FIGMA_PAT" \
  "https://api.figma.com/v1/files/<FILE_KEY>/nodes?ids=<PAGE_ID>"
```

Use the node data to understand component structure, variants, and properties.

> **Note:** The REST API returns raw Figma node JSON (not code).
> You must interpret the node tree (frames, variants, properties, fills, text styles)
> and translate it to Angular + SCSS using the conventions below.

## Step 4 — Implement New Components

For each approved Figma page:

1. Check if `Components/src/lib/<slug>/` exists
2. If it exists → skip to Step 5
3. If not → implement it (Steps 4a–4e)

### 4a — Hints

Check if `Agent/component-hints/<slug>.md` exists. If it does, read it fully before generating any files — hints take precedence over your default implementation choices.

Hints capture functional requirements that cannot be derived from Figma: interaction behaviour, input API decisions, edge cases, and constraints. They exist to keep component behaviour consistent over time as designs evolve.

**When to create or update a hints file:** Only when explicitly prompted by a developer. The developer provides the functional requirements in plain language; the agent's job is to write or update the hints file to record them clearly and concisely. Hints are never created or modified automatically during routine component implementation.

**When writing or updating a hints file:**

- Document what the component must do, not how it does it
- No implementation details — no class names, method names, signal patterns, or Angular APIs
- No visual or design details — colours, sizes, spacing come from Figma
- Requirements must stay valid regardless of how the implementation is refactored

If hints exist, use them as the source for the user-facing intro paragraph in the MDX docs. Keep hints and the MDX intro in sync — when the hints file changes, update the intro to match.

### 4b — Fetch Figma design data

Before writing any code, if any existing components are present under `Components/src/lib/`,
read at least one of them to absorb the current coding conventions, BEM naming, and test
style. If none exist yet, follow the conventions and templates in this instruction file.

Use the Figma REST API to fetch the page/frame for this component. Extract:

- Layer structure and nesting
- Variants and states (default, hover, disabled, active, sizes, etc.)
- Colors → map to `_tokens.scss` variables
- Typography → map to `_typography.scss` variables

- Icons → use `<iris-icon [name]="'<name>'" />` (`IrisIconComponent` from `@iris-ui/icon`).

#### The `Overview` story (add to `<slug>.stories.ts`)

The `Overview` story renders **all variants in a grid** so readers see every variant at once.

Rules:

- One row per variant (e.g. Primary, Secondary, Ghost, Danger)
- Each row shows: text-only, icon+text — or whatever columns make sense for this component
- If the component has a `disabled` input, expose it as `disabled: { control: 'boolean' }` in the Overview story's `argTypes` (with `args: { disabled: false }`), and bind `[disabled]="disabled"` on every element in the template so toggling the switch disables all instances at once
- Use a `render` function with an inline Angular template; bind `[size]` (and other cross-row inputs) from `args`
- **Expose all inputs as controls except the dimension used as rows** (e.g. `variant`, `type`) — hide only that row dimension via `table: { disable: true }`. All other inputs must appear in `args` and be bound in the template so the user can tweak them live. This is the opposite of hiding everything — hide only what is already represented as rows.
- **Always hide output events** (`output()` signals) in the story-level `argTypes` of **every** story that appears in an "Interactive Demo" section (typically `Overview` or `Interactive`). Use `outputName: { table: { disable: true } }`. Events must never appear in the Controls panel of an interactive demo — they cannot be set by the user and add noise.
- **Always declare outputs in meta `argTypes`** with a `description`, `table.type.summary`, `table.defaultValue.summary: '—'`, and `table.category: 'Events'`. The MDX `<ArgTypes>` block automatically groups them under an "Events" section. Without an explicit entry, Storybook may omit them entirely from the docs. Type summary should be the emitted value type only (e.g. `void`, `MouseEvent`, `TreeNode`) — never `EventEmitter<…>` or `OutputEmitterRef<…>`.

```typescript
export const Overview: Story = {
  args: { size: 'default', disabled: false },
  argTypes: {
    size: { control: 'select', options: ['sm', 'default', 'lg'] },
    disabled: { control: 'boolean' }, // always expose if component has disabled input
    // hide all other controls
    variant: { table: { disable: true } },
    label: { table: { disable: true } },
    buttonType: { table: { disable: true } },
    iconName: { table: { disable: true } },
    type: { table: { disable: true } },
  },
  render: (args) => ({
    props: args,
    template: `
      <div style="display:flex;flex-direction:column;gap:12px;">
        <div style="display:flex;gap:8px;align-items:center;">
          <iris-<slug> variant="primary"   [size]="size" [disabled]="disabled" label="Primary"></iris-<slug>>
          <iris-<slug> variant="primary"   [size]="size" [disabled]="disabled" buttonType="icon-text" iconName="confetti" label="Primary"></iris-<slug>>
        </div>
        <div style="display:flex;gap:8px;align-items:center;">
          <iris-<slug> variant="secondary" [size]="size" [disabled]="disabled" label="Secondary"></iris-<slug>>
          <iris-<slug> variant="secondary" [size]="size" [disabled]="disabled" buttonType="icon-text" iconName="confetti" label="Secondary"></iris-<slug>>
        </div>
        <!-- repeat for each variant -->
      </div>
    `,
  }),
};
```

#### `argTypes` requirements (apply to the meta in `<slug>.stories.ts`)

Every component input must have both fields set — Storybook does **not** infer these from TypeScript:

```typescript
argTypes: {
  variant: {
    control: 'select',
    options: ['primary', 'secondary', 'ghost', 'danger'],
    table: {
      type: { summary: "'primary' | 'secondary' | 'ghost' | 'danger'" }, // exact string literal union
      defaultValue: { summary: 'primary' },                               // component class default
    },
  },
  size: {
    control: 'select',
    options: ['sm', 'default', 'lg'],
    table: {
      type: { summary: "'sm' | 'default' | 'lg'" },
      defaultValue: { summary: 'default' },
    },
  },
  disabled: {
    control: 'boolean',
    table: {
      type: { summary: 'boolean' },
      defaultValue: { summary: 'false' },
    },
  },
  // ... one entry per input()
},
```

Never write just `{ control: 'select', options: [...] }` — always include the `table` block.

When a component input has a default value, three places must all agree:

1. The component class default (e.g. `input('tooltip')`)
2. The `argTypes` table entry: `defaultValue: { summary: "'tooltip'" }`
3. The `Overview` story `args`: `{ label: 'tooltip', … }`

Always update all three together — if any diverges the interactive story starts in the wrong state and the docs table shows the wrong default. This applies equally when changing a string literal union type (e.g. adding or renaming a variant in the model) or changing an `input()` default — the `options` array, `type.summary`, `defaultValue.summary`, and story `args` must all be updated in the same change.

Every arg that appears in a story's `args` and is not disabled via `table: { disable: true }` in `argTypes` **must be bound in the template**. If a story uses a custom `render` function, every active arg must appear as `[prop]="prop"` in the template — never hardcoded (e.g. `[disabled]="true"`) and never omitted. A control that has no effect on the rendered output misleads the user. Equally, never bind a prop in the template that is not present in the story's `args` — this passes `undefined` to the component and overrides its signal default, which can cause `NaN` values or broken behaviour at runtime.

Every component input must also have a `description` field explaining what the prop does in one concise sentence. If the prop is only meaningful in a specific mode or context (e.g. only in dual-thumb mode), the description must say so explicitly, and the prop must be placed in a named `table.category` matching that mode (e.g. `category: 'Dual thumb'`). Props that apply in all modes need no category. This text appears next to the type in the API table and is the primary way users understand each prop.

#### MDX rules

- **`<Canvas>` + `<Controls>` always go together in `## Interactive Demo`.** Every `<Canvas of={...Stories.Overview} />` MUST be immediately followed by `<Controls of={...Stories.Overview} />` on the next line — without `<Controls>`, the user has no panel to toggle the controls and the Interactive Demo section is useless.
- **Never hardcode `[disabled]="true"` in any Overview template.** If the component has a `disabled` input, expose it as a boolean control (see Overview story rules above) and bind `[disabled]="disabled"` on every element.
- **Omit sections that do not apply.** No `## Sizes` if there is no `size` input. No `## Disabled state` if there is no `disabled` input. No `## When to use` table if there is only one variant. No description sentence under `## Interactive Demo` if the canvas is self-explanatory.
- **`<ArgTypes>` always**: `sort="alpha"` + `of` pointing to the whole stories module (e.g. `of={ButtonStories}`), never to a single story, so all props from meta are shown without story-level overrides.
- **Interactive sections**: any section containing a `<Controls>` block must have the suffix ` — Interactive Demo` in its heading. A simple interactive section uses `## Interactive Demo`; a section for a specific mode uses the pattern `## <Mode> — Interactive Demo` (e.g. `## Single thumb — Interactive Demo`).
- **No lorem ipsum.** Use real label text from Figma or realistic examples.
- **Markdown tables work** — `remark-gfm` is enabled globally in `main.ts`.
- **Hints → MDX intro**: The intro paragraph below `# <Name>` is always a user-facing rephrase of `Agent/component-hints/<slug>.md`. Read the hints file first, then write the intro in plain language: what the component does, its key behaviours, and constraints. No implementation details in the intro — translate "flag", "pointerdown", "linkedSignal()" etc. into user-visible terms. When the hints file changes, update the intro to match.

## Rules

1. **Hints take precedence** — always check `Agent/component-hints/<slug>.md` before implementing or updating
2. **Tokens only** — zero hardcoded hex values, pixel sizes, or font definitions in SCSS
3. **Standalone components** — never create NgModules
4. **One commit per component** — clean history, easy rollback
5. **Do not remove existing exports from `public-api.ts` during routine sync/update work** — only remove an export when the corresponding component is intentionally being removed or deprecated
6. **Do not stop on a single failure** — log the error, skip that component, continue with the rest
7. **No lorem ipsum** — use actual label text from Figma or a realistic example
8. **Storybook must compile** — before committing, run `pnpm run storybook:build` and fix all compilation errors. A component is not done until Storybook builds cleanly.
9. **Linting must pass** — run `pnpm run lint` (or the project's configured linter) and fix all errors and warnings before committing. Do not suppress or disable lint rules without justification.
10. **Tests must pass** — run `pnpm test` and ensure all unit tests pass before committing. Every `input()` must have at least one test covering a non-default value. Aim for meaningful coverage of component logic: state changes, user interactions, conditional rendering, and edge cases (empty inputs, disabled states, boundary values). Do not leave the repo in a state where `pnpm test` fails with "No tests found": if all specs are removed, update the Jest config/script so a component-less baseline can still pass (e.g. `--passWithNoTests`).
11. **Use `setInput()` in tests** — prefer `fixture.componentRef.setInput('name', value)` over direct property assignment. This ensures Angular's signal-based change detection picks up input changes correctly.
12. **Use modern Angular style** — avoid deprecated syntax; specifically:
    - Use `@if`, `@for`, `@switch` (block control flow) — never `*ngIf`, `*ngFor`, `ngSwitch`
    - Use `input()`, `output()` signal-based APIs — never `@Input()` / `@Output()` decorators, never `model()`. **Exception**: components that implement `ControlValueAccessor` (CVA) must use `model()` for the bound value because `writeValue()` must be able to mutate it — `input()` is read-only and cannot satisfy the CVA contract.
    - For two-way bindable state on non-CVA components, use `input()` + `output()` with an internal `linkedSignal()`: declare `foo = input<T>(default)`, `fooChange = output<T>()`, and `readonly fooState = linkedSignal(() => this.foo())`. The template reads `fooState()`; mutations call `this.fooState.set(v); this.fooChange.emit(v)`. This lets the parent drive the value via `[foo]` while the component also updates it internally.
    - Use `inject()` for dependency injection — never constructor injection
    - Components must be standalone (`standalone: true`) — never use NgModules
    - Prefer `OnPush` change detection strategy for all components
    - Use `computed()` for any derived value that reads signals — never a plain getter. Getters re-run on every change detection cycle; `computed()` is memoized and only recalculates when its signal dependencies change.
