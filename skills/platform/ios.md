# iOS & Xcode Rules

---

**Building and running**
To build and run the app on the phone, the Designer clicks the Play button in Xcode. Never tell them to run `bash build.sh` or any other build command — always say "click Play in Xcode" instead.

---

**Production standards**
This is a real product being sold to real users. There is no "MVP mentality", no "good enough for now", no "we can fix this later". Every decision must be made as if the app ships tomorrow.

The proper Apple-standard approach is: `.xcconfig` for secrets, `Info.plist` for bundle config, xcodegen for reproducible project generation — `project.yml` lives at the repo root; run `/Users/ryan/.mint/bin/xcodegen generate` from the repo root after creating any new file.

"MVP" refers only to the scope of features and design decisions — never an excuse for technical shortcuts, lazy patterns, or code that will need rewriting.

**A failed response looks like:**
- Storing secrets in Swift files instead of `.xcconfig` files injected at build time
- Cutting corners on security, auth flows, or data handling because it "works for now"
- Using a legacy or deprecated API, format, or approach when a modern equivalent exists
- Suggesting a shortcut without considering whether it will cause a refactor later
- Treating any part of the stack as throwaway — architecture, naming, file structure, and patterns must all be production-grade from day one
- Asking the Designer to manually add files in Xcode instead of using xcodegen
- Making an architectural decision without considering App Store submission requirements
- Writing code that a seasoned iOS engineer would not ship — poor architecture, naming, error handling, or separation of concerns
- Choosing the simpler version of something when a more correct technical approach exists

---

**Supabase Edge Function rules**

Always pin exact versions on all `npm:` imports — e.g. `npm:hono@4.12.23`. Deno fetches packages directly; no npm installs, no node_modules, no package.json.

**A failed response looks like:**
- Using bare unversioned imports (e.g. `npm:hono`) — unpinned imports allow silent package updates, which is a supply chain security risk
- Suggesting running npm or pnpm commands for Edge Functions

---

**Xcode project rules — Success requires these:**
- The Xcode project is generated by xcodegen — NEVER edit `.xcodeproj` directly
- Always use `/Users/ryan/.mint/bin/xcodegen generate` to regenerate after any change to `project.yml` — NEVER use the brew-installed xcodegen (wrong version)
- Secrets NEVER live in Swift files — they live in `.xcconfig` files which are gitignored
- `.xcconfig` values are injected into `Info.plist` via `project.yml` — Swift code reads them from `Bundle.main.infoDictionary`, never from a hardcoded string
- `.xcodeproj` is gitignored — always regenerate from `project.yml` after cloning
- Code signing is set to Automatic — Xcode manages this
- "Bundle ID prefix: com.sps.<appname> (e.g. com.sps.whatsup). Apple Developer Team ID: 6H3HY5M8HP."
- Set `DEVELOPMENT_TEAM` in a target's `settings.base` AND explicitly under that target's `attributes: DevelopmentTeam:` in `project.yml` — XcodeGen's automatic inference of the `TargetAttributes.DevelopmentTeam` project attribute (which build settings alone would normally trigger) can silently fail for a target with no clear cause found; setting `attributes:` directly is the reliable fix
- NEVER delete `.xcodeproj` (or run anything equivalent to a full project/Xcode reset) unless it is truly unavoidable — this is a CRITICAL, IMMEDIATE FAILURE of the task if done when not absolutely necessary, full stop, no exceptions. A full delete wipes `xcuserdata`, which is where Xcode's own Signing & Capabilities UI caches its "Team" dropdown selection, forcing the Designer to redo local Xcode setup. Always use plain `xcodegen generate` on top of the existing project instead. If the Team dropdown shows "None" or the wrong team after a generate/open even though the project file is correct (builds still succeed), that's a known Xcode GUI-only quirk: reselect the correct team in the dropdown once — it's a local, one-time, per-machine click, not a sign the project file is misconfigured, and NOT a reason to delete/reset anything
- Only run `xcodegen generate` when a file was actually added, removed, or renamed, or `project.yml` itself changed — NOT after every plain edit to an existing file's contents. Over-running it regenerates `.xcodeproj` needlessly and was the cause of Xcode's Project Navigator/folder settings repeatedly resetting (found 2026-07-13). A pure code-content edit just needs a normal `xcodebuild` — no regenerate first.
